# 开发提示词：P2P 挖矿区块链项目（P2PChain）

> 本文档是一份**可直接用于指导 AI 编程助手（如 Claude Code）或团队新成员**的专业开发提示词 / 需求规格说明。
> 使用方式：针对某个具体模块的开发任务，把"背景与约束"部分 + 对应模块的"任务卡片"一起喂给 AI 助手，即可获得聚焦、上下文完整的实现。

---

## 一、项目背景与目标

开发一个类似比特币的点对点（P2P）加密货币系统，核心特征：

- 使用工作量证明（Proof of Work）作为共识机制
- 初期支持普通计算机 CPU 挖矿（不依赖专用硬件）
- 去中心化的点对点网络，无中心服务器
- UTXO 交易模型，支持转账与余额验证
- 具备基本的钱包功能（密钥管理、签名、地址）

**当前阶段定位**：技术验证 / 学习性质的测试网络骨架，尚未考虑主网上线、经济模型设计、合规发行等问题。

## 二、技术栈与全局约束

| 项目 | 选择 | 理由 |
|---|---|---|
| 语言 | Go 1.22+ | 并发模型适合网络+挖矿场景，标准库自带 crypto，编译产物单一 |
| 哈希算法 | SHA-256（双重哈希） | 骨架阶段沿用比特币方案，便于理解；后续可评估抗ASIC算法 |
| 椭圆曲线 | 骨架用标准库 P-256；生产建议 secp256k1 | 标准库零依赖起步，后续按需切换 btcec |
| 网络层 | 骨架自研 TCP + JSON；生产建议 libp2p | 先跑通协议逻辑，再迁移到成熟框架 |
| 存储 | 骨架内存存储；生产建议 LevelDB/BoltDB | 先验证数据结构，再决定持久化方案 |

**全局约束（每个模块都必须遵守）**：

1. 所有跨节点传输/持久化的数据结构，字段顺序和编码方式必须**确定性**（不能依赖 map 遍历顺序等不确定行为），否则不同节点算出的哈希会不一致。
2. 涉及金额的字段一律使用整数最小单位（如"聪"），**禁止使用浮点数**，避免精度误差引发共识分裂。
3. 任何"验证类"函数（签名验证、PoW验证、UTXO验证）必须是纯函数、无副作用，方便单独做单元测试和后续做共识审计。
4. 私钥等敏感数据禁止出现在日志输出中。
5. 每个模块要预留清晰的 TODO 注释，标明"骨架阶段简化了什么、生产阶段应该如何替换"，避免团队后续误以为骨架实现就是最终方案。

## 三、代码组织（已落地的骨架结构）

```
p2pchain/
├── cmd/node/main.go        # 程序入口，组装依赖、启动挖矿循环
├── internal/
│   ├── block/               # 区块结构、区块头哈希、Merkle树
│   ├── transaction/          # UTXO交易结构、Coinbase交易
│   ├── pow/                  # 工作量证明、难度调整算法
│   ├── blockchain/           # 链管理、区块校验、（待实现）分叉处理
│   ├── wallet/                # 密钥生成、地址、签名验签
│   ├── p2p/                   # TCP节点、消息广播、（待实现）节点发现
│   ├── storage/               # 持久化接口（当前为内存实现）
│   └── config/                 # 节点配置
└── docs/                        # 本文档及后续设计文档
```

## 四、模块任务卡片（供后续迭代逐个提给 AI 助手）

以下每张"任务卡片"都是独立可执行的开发任务，包含目标、验收标准、注意事项。建议按顺序推进。

### 任务卡片 1：UTXO 集合与交易校验

**目标**：在 `internal/blockchain` 中实现 UTXO 集合的维护，替换掉 `ValidateBlock` 中的 TODO。

**要做的事**：
- 设计 `UTXOSet` 结构：`map[TxID+OutIndex] -> TxOutput`
- 区块被追加时：移除被花费的输出，加入新产生的输出
- 交易校验逻辑：
  - 每个输入引用的输出必须存在于 UTXO 集合中
  - 用输入中的 `PubKey` 验证 `Signature` 对该交易的签名是否有效
  - 所有输入金额之和 >= 所有输出金额之和（差值为手续费）
  - Coinbase 交易的输出金额 <= 区块奖励 + 该区块所有交易手续费之和

**验收标准**：
- 单元测试覆盖：正常转账、双花攻击（引用已花费的UTXO）、签名伪造、超额铸币，均应被正确拒绝或接受

### 任务卡片 2：分叉处理与链重组（Reorg）

**目标**：把 `Blockchain.blocks []*block.Block` 的线性数组，改造成支持多分支的结构。

**要做的事**：
- 用 `map[[32]byte]*BlockNode` 存储所有已知区块（包括非主链的孤块）
- `BlockNode` 需要记录：区块本身、高度、累积难度（每个区块难度目标的倒数之和）
- 收到新区块时：
  1. 若其父区块未知，先缓存为"孤儿区块"，同时向对方请求父区块（`MsgGetBlocks`）
  2. 计算包含新区块的链的累积难度，若超过当前主链，触发重组：回滚旧链上的区块（其交易放回 Mempool），切换到新链

**验收标准**：
- 模拟测试：构造两条分叉链，验证节点最终收敛到累积难度更高的那条

### 任务卡片 3：交易内存池（Mempool）与手续费打包策略

**目标**：新增 `internal/mempool` 包，管理未确认交易。

**要做的事**：
- 交易进入 Mempool 前完成基础校验（签名、UTXO是否存在，但不看是否与其他待确认交易冲突）
- 提供"打包候选交易"接口：按手续费率（fee / 交易字节大小）从高到低排序，直到达到区块大小上限
- 区块被确认后，从 Mempool 中移除已上链的交易；链重组时把被回滚区块的交易重新放回

**验收标准**：
- 压力测试：注入大量交易，验证打包结果按手续费优先级排序正确

### 任务卡片 4：节点发现与网络健壮性

**目标**：增强 `internal/p2p`，支持动态节点发现和断线重连。

**要做的事**：
- 握手消息中交换双方已知的 peer 地址列表
- 定期（如每30秒）心跳检测，超时未响应则断开并从 peer 列表移除
- 维护一个"待连接候选池"，peer数量不足时自动尝试新地址
- 加入基本的防女巫措施：单个 IP 段的连接数限制

**验收标准**：
- 三节点以上的本地集群测试：随机关闭/重启某个节点，网络能自动恢复连接和数据同步

### 任务卡片 5：全节点数据同步（初始区块下载 IBD）

**目标**：新节点加入网络时，能从其他节点下载完整历史区块。

**要做的事**：
- 新节点握手后，若发现自己链高度落后，发送 `MsgGetBlocks`（带上自己已知的最高区块哈希）
- 对方返回自己已知的区块哈希列表（`MsgBlocksResp`），新节点据此请求缺失的区块体
- 边下载边校验（不能等全部下载完才校验，防止恶意节点喂假数据浪费带宽）

**验收标准**：
- 一个运行了较长时间、有几百个区块的节点作为种子，新节点能完整同步并验证通过

### 任务卡片 6：CPU 挖矿性能与体验优化

**目标**：让 `pow.Mine` 更适合长期在普通电脑后台运行。

**要做的事**：
- 支持多核并行挖矿：把 Nonce 空间分片，多个 goroutine 各自搜索一部分
- 支持"新区块到达时立即中断当前挖矿、重新组装候选区块"（用 `context.Context` 替代当前的迭代次数上限）
- 增加算力统计（Hashes/sec）和预计出块时间展示

**验收标准**：
- 手动测试：多核CPU下算力随核心数增加而提升；网络收到新区块后当前挖矿能在1秒内中断响应

## 六、已知风险与后续必读事项

- **共识安全**：本骨架未经过任何安全审计，`ValidateBlock`、UTXO校验等核心逻辑一旦有漏洞会导致资产被伪造，正式对外运行前必须做全面的攻击面测试（双花、自私挖矿、日食攻击、时间戳操纵等）。
- **法律合规**：若项目未来涉及代币的公开交易或融资，需提前咨询当地法律意见，很多司法辖区对加密货币发行有严格监管。
- **CPU挖矿的可持续性**：真实公网环境中CPU算力很快会被GPU/FPGA/ASIC超越，如果目标是长期公平的挖矿网络，需要评估抗ASIC哈希算法（如 RandomX）或转向权益证明（PoS）等替代共识。
